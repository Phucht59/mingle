# Telemetry purpose register — proposed, collection disabled

Updated 2026-10-02. This is the canonical purpose/minimization register for proposed product observations. The earlier [exploratory telemetry specification](EXPLORATORY_TELEMETRY_SPEC.md) supplies compatible architectural cautions; this register adds explicit questions, retention and removal decisions. It does not add a collector, endpoint, analytics service, command, schema or background network request. Phase 3 HOLD.

**Telemetry != command.** Future mobile keeps separate durable command and telemetry queues. A delivered telemetry event cannot authorize scoring, progress, permission, publication or server acknowledgement. Those require the server-authoritative domain record and its contract. No human data is collected by this task.

Privacy classes below: **P1** = coded coarse interaction/context metadata; **P2** = potentially sensitive learning behavior, assistance or task evidence even without raw content. Neither class permits identity, health inference or raw answer/voice data. “Optional: yes” means research/analytics emission is optional and may be disabled without disabling the product; it does not make authoritative business commands optional. **RW** = minimum approved study/decision window plus explicitly approved review period; exact TTL, access and deletion owner are UNSET and must be approved before any collection. Do not retain everything indefinitely for possible future ML.

## Duration, return and delayed evidence — fields/joins, not new truth

`estimated_duration` is revisioned content metadata. `actual_duration` requires declared wall/active-time semantics, pause/background handling and a clock-quality flag; an elapsed UI timer alone is insufficient. Attach minimal duration/stage context only to the approved activity/session question, rather than sampling every tap. Completion, abandon stage, resume, assistance and voluntary next session are separate observations. Return intervals derive from reliable eligible-use occasions; a missing event can be disabled telemetry, offline capture or withdrawal.

`delayed_retrieval` is a **learning evidence question**, not permission to trust a client correctness payload. Derive it from validated fresh independent assessment occasions, exact delay/conditions/revisions and authoritative accepted responses; preserve scheduled, observed, unavailable and missing prompts. Do not create a new competing business event/score solely for analytics. Definitions and denominators: [measurement framework](MINGO_PRODUCT_MEASUREMENT_FRAMEWORK.md).

## Common minimal envelope and prohibitions

Future fields are a conceptual minimum, not an approved API schema: coded session/attempt/occasion identifier where needed; event/stage type; objective/content/item exact revision where needed; assistance/replay conditions; explicit prompt source; event time, availability/knowledge time, source capture and capture quality; consent/purpose version and policy version where relevant. Avoid unused identifiers and fields. Distinguish fixture vs pilot/runtime and local-save vs server-ack source. Deduplicate retries; late capture cannot become information known at a past decision.

Do not send raw answers, free-text search, diary text, email/name, password/token, microphone audio, precise location, school/medical data, device advertising ID or a behavioral “bored/lazy” label. Optional self-report belongs to a consented research form with redaction and separate access, not an unrestricted event payload. Feedback-viewed does not imply understood; replay does not imply heard; duration does not imply attention.

## Collection gate and lifecycle

Before a later approved pilot/runtime: name the product decision, map to the table, confirm that a less intrusive source cannot answer it, define TTL/access/deletion and withdrawal treatment, obtain applicable consent/disclosure, validate event capture and authority boundaries, and test queues/retries/late arrival without affecting commands. During review remove events/fields that no longer support a decision. Audit telemetry-disable behavior: no loss of basic product function or scoring/progress authority.
